# Forge：定理铸造厂

以 Lean 内核为唯一裁判，把"提出命题 → 证明或证伪 → 入库 → 被后续证明引用"做成一条可并行的流水线。
产物是 `lean/Mathlib2/`：一个真正能 `import`、能互相引用、随时可 `lake build` 的 Lean 库。

## 为什么是这个形状

调研结论（见仓库讨论）：证明器、检索器、论文形式化 agent 都已有开源实现，没有必要重写。
没人做完的是这几段，本模块只做这几段：

| 缺口 | 这里的做法 |
|---|---|
| 机器生成的结果互不相通，没有统一的库 | 所有通过准入的定理进同一个 Lean 库，后来的证明可以直接引用前面的 |
| 重复和平凡命题淹没有价值的 | 入队前分诊：`exact?` 一步即得的不收；结构哈希相同的判重；能被常用自动化关掉的标为 `tier=auto` |
| 假命题浪费证明预算 | 入队前用 `plausible` 随机测试找反例（实数命题换成有理数再测一次），有反例的直接转去做形式化证伪 |
| "什么算有价值"没人回答 | 给出可解释的排序信号：是否需要 agent 才能证出、被多少后续证明引用、是否证伪了一个猜想 |
| 命题译得对不对内核管不了 | 论文命题保留原文，由独立 agent 复核并记录结论，最终由人采信；不把它混进"已验证"里 |

## 四个目标各自怎么落到这条流水线上

1. **审核已有论文**：`forge paper x.pdf` 提取命题清单 → agent 译成 Lean 命题并 `propose --origin paper` →
   已在 Mathlib 里的当场判为 `known` 并指出对应定理，其余进队列 → `forge review` 记录忠实度复核。
2. **AI 原生的 Mathlib2**：`lean/Mathlib2/Shard/*.lean`，追加式分片，每次入库后整库重建，失败即回滚。
3. **搜索已有证明并拆成引理 DAG**：`forge search` 检索库；`forge sketch` 提交带 `sorry` 的证明骨架，
   由内核把每个空洞处的目标提取成子任务；子任务证完后 `forge assemble` 自动拼回。`forge dag` 的边来自证明项里实际引用的常量。
4. **大量 agent 并行提问题并证明或证伪**：任务领取是原子的，入库有锁，多开进程即可并行；`forge report` / `forge catalog` 给数学家挑选。

## 信任边界

裁判在 Lean 一侧（`lean/Forge.lean`），Python 不解析人类可读的输出：

- `#forge_info`：直接从环境读常量的类型、公理依赖、证明项引用的常量。只接受 `propext`、`Classical.choice`、`Quot.sound`。
- `#forge_match`：提交的定理类型必须与任务命题（证伪时是其否定）定义等价，防止偷换命题。
- 每次调用带随机 nonce，提交内容无法伪造这些输出。
- 提交文本只允许 `open` 行和 `theorem`/`lemma` 声明；`axiom`、`def`、`instance`、`notation`、`macro`、`set_option`、
  `native_decide`、`run_tac` 等一律拒绝。这一层是纵深防御，不是主要保证。
- 入库后整库 `lake build`，出现 `sorry` 警告或构建失败就回滚。

已知局限，没有解决：

- 文本黑名单挡不住所有改变语义的手段；更强的做法是用 `lean4checker` 或独立的比较器重放 `.olean`，尚未接入。
- 判重靠类型的结构哈希，只能识别 α 等价的命题；改写过的等价命题（交换假设顺序、移项）识别不了。
  `exact?` 能挡住一部分（库里已有的会被一步找到）。
- 平凡性分层取决于当前的自动化阶梯，`tier=agent` 只表示"这几个策略一步关不掉"，不代表深刻。
- 骨架空洞的目标靠 pretty-print 再解析，带隐式宇宙或匿名假设时可能回不来，届时会明确报错。
- 忠实度复核是 agent 的判断，不是证明。

## 设计上借鉴的工程做法

主要参考 Anthropic 工程博客里关于构建 agent、多 agent 系统、给 agent 写工具、以及用并行 Claude 写 C 编译器的经验
（本次会话无法抓取原文，以下是按其思路落地的做法，不是引文）：

- **先用最简单的结构**：分诊是固定流程（一次 Lean 运行），只有真正开放的部分才交给 agent。
- **验证器当裁判，库永远保持可构建**：等价于"测试必须一直是绿的"，入库有门禁和回滚。
- **用文件锁/原子 rename 认领任务**：多个 agent 无需协调者也不会撞车。
- **工具输出为 agent 的上下文着想**：错误只给前几条、带相对行号、截断长消息；成功时给下一步该做什么。
- **把失败留给后来者**：`release` 必须写明试过什么，下一个 agent 领到任务时能看到。
- **规模与难度匹配**：自动化能关掉的不派 agent；agent 做不动的拆成子任务而不是无限重试。

## 用法

```bash
./forge.sh status
./forge.sh propose --name my_claim --statement "(a b : ℕ) (h : a ∣ b) (hb : 0 < b) : a ≤ b"
./forge.sh next --agent me
./forge.sh check my_claim proof.lean
./forge.sh submit my_claim proof.lean --agent me
./forge.sh report
```

完整命令和提交格式见 [AGENT_GUIDE.md](AGENT_GUIDE.md)。

驱动它的 agent 可以是任何能跑命令行的东西。仓库里附带一个直接用 Anthropic SDK 的自主 worker：

```bash
.venv/bin/python -m forge.worker prove --agent w1 --tasks 5
.venv/bin/python -m forge.worker conjecture --agent c1 --area "初等数论" --count 10
```

它需要 Anthropic 凭据（`ANTHROPIC_API_KEY` 或 `ant auth login`），默认模型 `claude-opus-5-5`。
**这个 worker 只做过导入和参数检查，没有对真实 API 跑过**——本机没有配置凭据。首轮战役是由 Claude Code 的子 agent 通过命令行完成的。

### 论文三的发现

`paper_3` 自行在 arXiv 选了这篇短文并通读。它报告定理 1 按印刷表述不成立，独立复核 agent `reviewer_3` 重新读了原文
（v1、v2、v3 三个版本）并用脚本独立计算，确认了这一点：

- 论文称素数 p > 5 时 S_p = F_1 + … + F_p 模 p 余 3（p ≡ ±1 mod 5）或余 1（p ≡ ±2 mod 5）。
- 对 5 < p < 200 的全部 43 个素数，印刷的结论一个都不成立（例如 S_7 = 33 ≡ 5 mod 7）；各种可能的读法也都不成立。
- 正确的余数是 1 和 −2。库里有印刷版本的证伪（`p3_thm1_disproof`）和修正版的证明（`p3_thm1_corrected`，已标注为审核者的修正而非论文原文）。
- 笔误在证明里二项式展开的 k = 0 项：写成 C(p+2,1)·5，应为 C(p+2,1)·5⁰。

限定：这是旁支结论里的计算笔误。“p ∤ S_p” 仍然成立，论文的主要结果（命题 2、定理 2、推论 2）不依赖这组余数，都已证出。
复核只看了 arXiv 版本，期刊正式版可能已更正。尚未有人类核对，也没有联系作者。

### 论文四（arXiv:2503.03469v1，一个受 Erdős 启发的整数不等式）

`paper_4` 自选并通读，29 条命题全部有内核结论（28 证明、1 证伪），4 条新定义；`reviewer_4` 独立重读原文并用脚本算到 n = 300000。

- 论文的全部编号命题都成立，包括主定理：x(n) = 0 当且仅当 n ∈ {436, 451, 529, 545, 546}，n ≥ 547 时恒为正，最小值 −59 仅在 n = 129 取到。
- 定理 1(v) 的一行证明里，“若 2^(k+2) > 3B+1 则 x(2^(2k+2)) > B”按字面在 k ≤ 3 时不成立（如 x(16) = −15），k ≥ 4 时成立。
  该句开头写明“考虑到 Remark 1”，而 Remark 1 的界本身带着 k ≥ 6，所以复核者的结论是**漏写了继承来的条件，属于不严谨，不是证明错误**；定理成立。
  第一个 agent 最初的说法（“证明中有一步是错的”）偏重，这里采用复核后的措辞。
- 引理 1(ii)(iii) 的若干假设在证明中用不到（陈述比证明所能给出的弱）。

### 实战暴露并修掉的问题（这几轮）

- 骨架拆解：某个空洞无效时留下孤儿子任务并堵死重试；带 ∃ 的目标打印后解析不回来；拼装不带上下文参数而失败；
  别人能给不属于自己的父任务另起骨架；重新拆解不清理旧子任务；`<;> sorry` 一个 sorry 管多个目标不被接受；
  空洞文本解析回去**含义变了**（置换乘积被读成逐点乘积）——现在提取时当场核对，不一致就拒绝登记。
- 分诊：缺类型类实例的病态命题被误收；求值类检查卡死把合法命题误判为无效；机器繁忙时超时被误报为无效。
- 队列：别的 agent 能抢交或归还不属于自己的任务；指名领取已结束的任务却返回成功。

### 这些数字的含义

- 库从 68 条长到 475 条，领域从数论和不等式扩到十来个方向，但**规模仍比 Mathlib 小三个数量级以上**。
- 绝大多数命题是已知的经典结论；“Mathlib 一步得不到”不等于“新”。真正算得上发现的只有论文三的那个笔误。
- 两个环节有效：让出题 agent 读库并“往上搭”（依赖深度 2 → 8），以及“推广者”角色（18 条推广全部成立）。
- 随机测试对带整除或素数假设的命题、对实数命题经常抓不到反例；agent 自己拆出的假引理有好几次是靠人工小例子或证明失败才发现的。
- 5 小时用量限额在 7 个 agent 并行时约两个半小时用完；之后控制在 3–4 个并行。

## 无人值守开跑前的加固（2026-11-15 中午）

为了让外部模型（例如 Codex/GPT）大规模、无人值守地跑，补了四件事。设计思路是：数量指标一定会被钻空子，
所以“收什么”和“怎么算进步”都要由内核和固定评测来定，而不是由 agent 自己说。

| 加固 | 做法 | 实测 |
|---|---|---|
| 空真命题 | 分诊时另跑一组探针 `example <签名假设> : False`（`simp_all`、`omega`、`linarith`、`nlinarith`、`tauto`、`contradiction`、`aesop`）；能推出 False 就判 `vacuous` 拒收。只看冒号前的假设，不拆结论，避免把 `¬P` 误判 | 构造的 `n < 3 ∧ 5 < n` 被拦下；队列里抽查的正常题无误判 |
| 换了写法的重复 | 用词法检索取最相近的 5 条库内定理，看新命题能否只用其中一条一步推出（直接套用、`simp_all`、`solve_by_elim`、`grind`，以及先把子类型 card / `Finset.filter` card / `Set.toFinset` / `Nat.card` 统一写法再套用）；能就判 `known` 并写明出处 | 上午漏掉的 `calc_card_involutions_rec` 现在会被认出（由 `comb_card_involutions_rec` 推出）；`calc_card_no_adjacent_subsets`（`Fin n` 与 `ℕ` 子集之间要建双射）仍抓不到 |
| 入库吞吐 | 组提交：校验不持锁、并行；通过后放进待入库区，抢到锁的进程把当时排队的提交合并成一次 `lake build`。合并构建失败就整批回滚、逐条重来 | 3 份并发提交 16 秒全部入库（两条共用一次构建）；混入一份重复提交时，其余照常入库、重复的被拒并回滚 |
| 独立内核重放 | `./forge.sh audit --replay`：复用 Lean 核心的 `Lean.Environment.replay`（lean4checker 的核心），把 Mathlib2 的全部常量放进只导入 Mathlib 的新环境让内核重新检查；另外不许出现新公理和 unsafe/partial 声明 | 3272 个常量全部通过，约 80 秒、内存峰值约 14 GB；反例测试中塞进去的公理和 unsafe 声明都被报出 |
| 固定评测 | `bench-import` / `bench-check` / `bench-score`：评测题只判对错、不入库，按轮次记成绩；任何新命题或提交里的辅助引理与评测题相同即拒收，防止测试题泄漏进库 | 用自造的两题集合走通（一题因类型错误被丢弃；第一轮 0/1、第二轮 1/1；把评测题当新命题提交被拒为 `reserved`） |

### 评测集与调度器（同日下午）

- **评测集**：导入了 miniF2F 的 test 部分 243 题（`forge/data/bench/minif2f_test.jsonl`，来源、许可和所做的语法转换见
  `forge/data/bench/SOURCES.md`）。导入时核对过：库里没有任何条目或辅助引理与这些题命题相同。
- **调度器**：`./forge.sh run`，默认调用本机 Codex 命令行（`codex exec`，沙箱为 workspace-write，模型 `gpt-6.1-sol`、推理强度 `xhigh`，可用 `--model` / `--effort` 改），也可以用 `--agent-cmd` 换成别的 agent。

```bash
# 清队列：2 个工人，最多 10 道题，总时长 60 分钟，单题 20 分钟，连续 4 次没进展就停
./forge.sh run --run 2026-11-16-a --prefix gr_ --workers 2 --max-tasks 10
# 跑评测：成绩只来自调度器自己的内核校验
./forge.sh run --run mf2f-r1 --bench minif2f_test --limit 20 --workers 3
./forge.sh bench-score minif2f_test
./forge.sh run-report 2026-11-16-a
```

  调度器只认内核的结论：队列模式看任务在库里的最终状态，评测模式自己重新校验 agent 留下的证明文件；agent 没做完就由调度器代为归还并记下原因。
  每次调用记一行账（耗时、Codex 报告的 token 数、最后一条消息），超时会结束整个进程组，不留 Lean 孤儿进程。

  269 题入队（其中 51 题随机测试已找到反例），26 题无效（20 题用了未定义的名字，例如把 a·b·c 写成 `abc`；关闭自动隐式变量之前
  这类题会被悄悄放行），2 题被自动化证出，1 题判为已知。随后用 Codex 清了其中 60 题：**60 题全部有结论，42 证出、18 证否**
  （证否说明这条 Lean 写法本身为假，即形式化写错了）。
- **分诊“可能为假”标记的准确度**（以这 60 道 Codex 给出内核结论的题为准）：被标记的 9 题全部被证否（精确率 100%），
  但 18 道假命题里只抓到 9 道（召回率 50%）。漏掉的主要是带等式约束的实数不等式（随机取值几乎碰不到 a + b + c = 3）
  和含 `Real.sqrt`、实数幂的命题（随机测试算不出值）。另外新增一条文本检查：命题里出现 `x ^ (1 / 3)` 这类写法时提醒
  “指数按自然数除法会变成 0”，试点 300 题中有 10 题如此；提醒会写进任务，证明者和复核者都能看到。
- **清队列提示词 A/B**（同批 Lean Workbook 任务按名字哈希分两组，各 30 题，xhigh、3 路并行）：v1（先读整份手册）30/30 有结论、
  81.7 万 token；v2（规则写进提示词）30/30 有结论、64.1 万 token（少 22%），用时相同。两组题目不同，严格程度不如评测集上的对比，
  但方向一致；清队列模式默认用 v2。
- **PutnamBench 抽样**（`putnam-s40-xhigh`：从不需要填答案的 312 题里固定抽 40 题，Codex gpt-6.1-sol、xhigh、提示词 v1、每题 30 分钟、每题只试一次）：
  **40/40 全部解出**，用时中位数约 4 分钟，每题约 4.7 万 token，共约 199 万 token。40 题全对时，在这 312 题上解出率的
  95% 置信区间下限约 91%。对照官方排行榜（分母 672，含需要填答案的题）：多家系统已 672/672，2025 年 GPT-5 单次尝试（ReAct 10 轮）为 28/672。
  PutnamBench 的 Lean 证明已有不少公开发布，可能出现在模型训练数据里，这个成绩同样要打折扣。
  同一组 40 题换用提示词 v2（`putnam-s40-v2`）：同样 40/40，共约 160 万 token（少 19%），用时中位数 207 秒（v1 为 226 秒）。
- **评测驱动的优化**（同一组 40 道 miniF2F 题，固定抽样 `--sample 40 --seed 7 --skip-refuted`，用 `run-compare` 对比）：

  | 轮次 | 推理强度 | 提示词 | 解出 | 总 token | 每题 token | 用时中位数 |
  |---|---|---|---|---|---|---|
  | `mf2f-baseline-1`（同 40 题） | xhigh | v1 | 40/40 | 75.9 万 | 1.90 万 | 63 秒 |
  | `effort-low` | low | v1 | 40/40 | 69.4 万 | 1.73 万 | 47 秒 |
  | `effort-medium` | medium | v1 | 40/40 | 77.6 万 | 1.94 万 | 47 秒 |
  | `effort-high` | high | v1 | 40/40 | 67.9 万 | 1.70 万 | 49 秒 |
  | `effort-low-v2` | low | v2 | 40/40 | 48.9 万 | 1.22 万 | 43 秒 |

  两条结论：这组题上四个推理强度都是 40/40，token 只在 ±7% 内随机波动，推理强度几乎不影响结果和成本（miniF2F 已饱和），成本的大头是上下文；
  v1 提示词让 Codex 每题先读完整的 `AGENT_GUIDE.md`（约 1 万字符，之后每轮对话都带着），v2 把评测需要的规则直接写进提示词，
  省了 30% 的 token、解出率不变。评测模式现在默认用 v2。

- **展示页**：`./forge.sh site` 改成面向非专业读者：一句话结论和四个关键数字，“计算机检查”的通俗解释，以及它不能保证什么；
  然后是精选成果（都是已知结论，逐条注明出处）、论文体检（红绿灯）和领域分布，最后才是给数学家的全部定理（可搜索、可收藏导出）。
  精选与论文结论的大白话写在 `forge/data/showcase.json`，可以由人或 agent 逐条补充，不用改代码。

- **两台电脑一起跑**：Windows 上用 `forge.cmd`（与 `forge.sh` 等价），安装和分工见 `forge/WINDOWS.md`。Mac 是主机、唯一写库；Windows 只用 `--shard` 跑一半评测题，轮次名带 `@win`，`bench-score` 会把两台的成绩合并。

剩下的局限：

- agent 在仓库里有写权限，理论上能改队列或日志文件；库的真实性要靠定期跑 `forge audit --replay`，评测成绩只采信调度器自己的校验。
- 一步推论检查只是“便宜的近似去重”：需要真正证明工作的等价重述仍会被收进来；空真检查也只覆盖自动化能找到的矛盾。
- 内核重放要同时载入两份 Mathlib 环境，在 16 GB 内存的机器上会很吃紧。
